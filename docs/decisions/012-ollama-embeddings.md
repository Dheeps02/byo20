# 012 — Bundled Ollama for Embeddings v1.0.0

## Status
Accepted

## Context

BYO20 uses vector embeddings for NPC memory retrieval (semantic recall for the NPC Specialist) and faction event memory. These embeddings must be generated consistently — the same text must always produce the same vector, regardless of which LLM provider the DM has configured.

The DM's LLM provider (Anthropic, OpenAI, Google, Ollama) is used for all generative tasks. Anthropic has no embedding model. Using the DM's provider for embeddings would require branching logic per provider, different vector dimensions per provider, and would fail entirely for DMs using Anthropic.

## Decision

BYO20 bundles its own Ollama instance, separate from any system-installed Ollama. This instance is used exclusively for embeddings — never for generation.

- **Model:** `nomic-embed-text` — 768-dimensional embeddings
- **Port:** `11435` — avoids conflict with a system-installed Ollama on `11434`
- **Storage:** Binary and model weights stored under `~/.byo20/ollama/` — fully scoped to BYO20, never touches the system Ollama installation
- **Management:** `electron-ollama` package — downloads the binary on first launch, spawned as a fourth sidecar alongside Postgres, Redis, and the game server
- **First launch:** Requires internet for a one-time ~350MB download (binary + model). A clear error is shown if the machine is offline during first launch.

The embedding dimension is fixed at 768. `npc_memories.embedding`, `faction_events.embedding`, and `combat_log.embedding` all use `vector(768)`.

## Alternatives Considered

**Use the DM's LLM provider for embeddings** — Rejected. Anthropic has no embedding model. OpenAI, Google, and Ollama each use different embedding models with different output dimensions. Supporting all four would require branching logic and per-provider dimension handling, complicating the Drizzle schema (the `vector(N)` column dimension is fixed at migration time) and adding provider-specific code paths to the AI layer.

**Hardcode OpenAI's text-embedding-3-small (1536 dimensions)** — Rejected. Requires OpenAI API access and incurs per-call cost. Doesn't work for DMs using Anthropic or local Ollama. Fails offline.

**ChromaDB as a dedicated vector database** — Already rejected in ADR 007. Bundled Ollama is the fourth sidecar; ChromaDB would be a fifth.

## Consequences

- Embeddings are always generated by `nomic-embed-text` via the BYO20 Ollama instance. Consistent 768-dimensional output, no provider branching, works offline after the first-launch download.
- First launch requires ~350MB of internet download. This is unavoidable and is clearly communicated in the UI.
- `~/.byo20/ollama/` is scoped to BYO20. DMs with an existing system Ollama on `11434` see no conflict.
- Electron main process manages four sidecars: Postgres, Redis, BYO20 Ollama, and the game server.
- The BYO20 Ollama instance runs only while the app is open. Embeddings are generated at event-log write time; there is no background embedding job.
